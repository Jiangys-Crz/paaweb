# rating-system

这个插件为 HydroOJ 提供 `cf_like_v1_4` Rating 系统，并把域内原有 RP 排行榜替换为 Rating 排行榜。`lib/rating.ts` 中的 v1.4 固定规则是本插件的结算依据；缺少 v1.4 固定配置的比赛不会结算。

## 功能

- 每个域内用户分别保存 `internal_rating`、`rating`、`rated_count` 和 `max_rating`；同时写入 camelCase 别名以兼容 Hydro 现有页面。
- 按 `lib/rating.ts` 中的固定规则实现初始实力分、新手展示补分、并列平均名次、动态整数二分、两次全场修正、展示分计算和最高分记录。
- 只有正式个人参赛、在公布的 Rating 分段内、比赛时间内至少有一次最终评测提交且没有被取消资格的用户进入计分集合。
- `System Error` 提交会被忽略，不计入参赛资格，也不参与成绩和 Rating 名次计算；用户存在其他有效最终评测提交时仍可正常计分。仍处于排队、编译或评测中的未完成记录会阻止正式结算。
- 计 Rating 的比赛在详情页使用页面中央弹窗选择“正式参赛（计入 Rating）”或“打星参赛（不计 Rating）”，不再使用浏览器顶部确认框，也不进行二次确认。当前 Rating 不在本场 `[ratedMin, ratedMax)` 范围内时，正式参赛选项禁用。选择写入 Hydro 原有参赛状态的 `unrank` 字段；`unrank` 未设置时默认正式参赛，设置为 `true` 时表示打星参赛。不计 Rating 的比赛只显示“确认报名？”弹窗，确认后直接报名，不显示参赛身份选择或身份修改按钮。未报名用户在比赛结束前均可报名；已经报名的用户只能在开赛前取消报名或修改参赛身份，两个操作按钮在同一行显示，开赛后页面不显示按钮且服务端拒绝取消和修改操作。
- `rated`/`is_rated` 为 `false`、有效计分人数不足 5 人、所有有效选手完全并列、比赛未结束或规则版本不是 `cf_like_v1_4` 时不会结算。
- 比赛编辑页提供 Rating 最低分（包含）和最高分（不包含）两个分段字段，默认值分别为 `0` 和 `10000`，保存到比赛文档的 `ratedMin`/`rated_min`、`ratedMax`/`rated_max`；插件按 XCPC、IO、IOI 的比赛类型固定 `contestType`/`contest_type`、`scoreRule`/`score_rule` 和 `cf_like_v1_4` 版本。
- 每场比赛冻结 `publisher_id`/`publisherId`；重算时直接以比赛编辑页当前的 `maintainer` 为该场比赛管理员名单，并兼容旧版本保存的 `contest_admin_ids`/`contestAdminIds`。这里的“比赛管理员”只指该场比赛 `maintainer` 中的用户，不包括平台管理员、超级管理员、教师或域管理员。本场发布者不进入正式比赛排名、Rating 集合或有效计分人数；比赛管理员只要不是本场发布者，就会进入 Rating 集合并固定按本场第一名计算，不要求报名、参与排名、符合 Rating 分段或有有效提交。管理员的实际比赛成绩不会改变普通选手的名次；其他管理身份只要符合普通资格，就按实际名次正常计分。
- 每天服务器本地时间 00:00 以及不指定重算参数的管理脚本 `rating` 都只结算尚未计算 Rating 的比赛：已经结算过的比赛不会再被重算，用户状态从数据库中已有的 Rating 继续累加，因此重复运行不会累加分数，也不会改写历史流水。每场比赛重新判断 Rated 配置、参赛资格、管理员名单、有效提交和名次；未结束、存在未完成评测或配置错误的比赛会留到下一次运行，不影响其他比赛结算。非 Rated 比赛不参与结算。
- 结算过的比赛会在比赛文档上写入 `ratingSettled` 标记，结算流水同样标记为 `settled`；标记与流水都会作为“已计算”的依据。若检测到 Rating 结果存在但没有可用标记（旧版本升级）或普通结算提交未完成，会先做一次完整重算来重建历史，之后继续按增量结算。指定比赛重算中断时，会保留并恢复原来的比赛范围和通知批次。
- 需要按初始 Rating 重新计算全部历史时，可以执行完整重算：`hydrooj script rating '{"full":true}'`，也可以同时传入 `domainId` 只处理一个域，例如 `hydrooj script rating '{"domainId":"system","full":true}'`。完整重算会重建所有用户状态与标记，并清理不再满足条件的结算结果。
- 尚未结算的比赛如果在已结算比赛之后才具备结算条件（例如分段、管理员名单或参赛状态调整后重新满足条件），会按当前 Rating 顺序结算并在日志中提示，不会回滚已写入的历史。
- MongoDB 副本集环境使用事务提交；单机 MongoDB 使用带批次标记的可恢复提交，不需要为了 Rating 结算额外配置副本集。未完成的暂存批次会在下一次成功重算时清理。
- 每场比赛结算成功后向本场获得 Rating 的用户发送一条未读系统通知，包含比赛名称、Rating 增加或减少的分值、结算前后分数和历史最高分。每次显式指定比赛或 `full=true` 重算都会建立新的通知批次，即使分值未变化也会发送“Rating 重算通知”；指定比赛重算还会通知被移除计分资格的原参与者。同一次提交的重试和崩溃恢复复用该通知批次，不重复发送；发送失败的记录在下一次计算时重试，未成功提交的重算结果不会发送。
- 域排行榜按当前 Rating 排序，同时显示当前 Rating 和历史最高 Rating。个人主页同样显示这两个分数；排行榜与首页排行榜中的个人简介最多显示 96 个字符。
- 用户名和显示名会根据 Rating 显示对应等级颜色；用户展示统一为“用户名（显示名）”，用户名按规则处理首个 Unicode 字素，括号中的显示名使用用户名除首字符对应的颜色。未定级用户显示黑色，用户徽标显示规则中的英文段位名，不再显示 Hydro 的 LV 等级。
- Rating 英文段位标识只在排行榜、首页排行榜和个人主页显示；讨论、通知、题目、比赛及其他用户列表中只显示带 Rating 颜色的用户名和显示名。
- 原 RP、RP 明细、题目/比赛/通过数量列不再参与 Rating 排行展示，旧字段会在重算时清零。
- 比赛页面主体保持与站内其他页面相同的居中宽度、卡片阴影和悬浮效果。顶部赛事横幅使用自包含 CSS 渐变背景，按 `2172:584` 比例显示。标题和信息限制在图片左侧文字区，标题使用加粗深蓝色，标签和值使用分层蓝灰色；背景仅覆盖 6% 黑色滤镜，让浅色图片保持明亮。比赛名称后固定显示 Rated/Unrated、赛制和当前比赛状态三个彩色标识。比赛信息固定分成两行：第一行显示开始时间、结束时间和时长，第二行显示题目数、主办者、报名人数和 Rating 范围；信息始终完整显示，窄屏时按完整字段换行且不出现滚动条，范围使用“最低值 ≤ Rating < 最高值”。比赛结束后，所有可访问比赛的用户均显示标签式导航，包括未报名用户；比赛结束前，普通用户仍需已报名且已开赛才显示导航；比赛发布者和该场 `maintainer` 始终拥有本场管理入口。其他平台、超级或域管理员在比赛结束前按普通用户权限展示，不能编辑、管理或导出代码，比赛结束后才恢复 Hydro 原有管理权限；这些限制同时在服务端校验，不能通过直接输入 URL 绕过。比赛说明、题目、排名和带比赛筛选的提交页面共用同一赛事卡片与横向导航，页面原有表格、筛选器、答疑和导出功能保留在导航下方。赛前使用“小时、分钟、秒”三个大号方块显示开始倒计时，每个灰色方块会按数字长度扩展；比赛开始后在导航右侧用三个紧凑色块显示结束倒计时，结束后显示“比赛已结束”。已报名用户停留在详情页直至开赛倒计时结束时，页面会自动跳转到本场题目列表。
- 比赛横向子导航依次排列“比赛说明、题目列表、排行榜、所有递交、我的递交、题解（讨论）、帮助、编辑比赛、比赛管理”，无权限的入口自动隐藏，打印和代码导出位于主导航之后；当前页面使用浅色背景块标记，不显示文字下划线。使用该子导航的比赛页面会隐藏网站顶部重复的“题目列表”和“比赛成绩表”，比赛题目详情页仍保留原生顶部入口。排行榜限制为与比赛详情相同宽度的悬浮卡片；所有递交和我的递交共用卡片，全站普通提交页面保持原布局。
- 比赛榜单和提交列表采用与主站外榜一致的字体、列顺序、行高和配色。XCPC 显示独立的序号、排名、学校、用户、解题数和分钟罚时；首 AC 深绿、AC 绿色、错误红色、封榜蓝色，底部显示提交、尝试、通过及首末通过时间统计。IO/IOI 使用四档得分背景，保留 Hydro 原有加权分数和赛后练习成绩。题目较多或窗口较小时整张表按比例缩放，不隐藏列。
- 榜单区域保留表格、动态搜索和 `Rating 排名 / 不计 Rating / ALL` 三种筛选，不显示进度条、导出和刷新按钮。搜索按用户名、学校、显示名即时模糊匹配，忽略英文大小写；可与参赛身份筛选组合使用，身份以 Hydro 原有 `unrank` 为准。学校和显示名仅为该榜单按字段读取，不把邮箱等其他私有资料加入搜索。自动刷新后继续使用当前搜索和身份筛选。
- 比赛提交列表使用英文表头、白蓝交替行、彩色判题图标和 `View Details` 链接。全部递交和我的递交共用行模板，WebSocket 更新后维持同一列结构；管理员可用的重测和取消成绩操作仍按原权限显示。作业及全站普通提交页面继续使用原生模板。
- 榜单与提交记录顶部筛选控件统一：高度 32px、圆角 6px、浅灰边框和 12px 间距，题目/状态/语言/参赛身份框宽度 150px，搜索框宽度 320px。提交页的自动补全组件加载后沿用相同尺寸、焦点样式、占位文字和无障碍标签。提交列表的表头、列定义和数据行使用相同列标识，并统一居中对齐，避免原生提交页列宽影响表头位置；即时更新和窄屏缩放使用同一表格网格。比赛榜单移除 Medal/Award 列，底部统计和表格缩放不再为该列留空。
- 比赛导航中的讨论入口显示为“题解（讨论）”。比赛结束前，只有比赛发布者和该场 `maintainer` 能查看、发布并按 Hydro 原有权限编辑本场讨论；其他参赛者以及不属于本场的管理员在比赛页面、全站讨论列表和首页中均看不到已发布的本场讨论，服务端也会拒绝讨论列表、详情、创建、回复、编辑和原始内容 URL。比赛结束后自动恢复正常讨论权限。
- 比赛结束前，除比赛发布者和该场 `maintainer` 外，普通用户、平台管理员、超级管理员和域管理员访问任何带本场比赛上下文的页面时，当前请求都会被限制为普通账号权限：只能查看自己的提交记录详情和代码，不能查看他人的提交列表、详情或代码，也不能通过提交详情下载地址和实时连接绕过。自己的提交详情和列表中不会显示“重测”或“取消成绩”等管理操作；编辑、管理、代码导出、隐藏排行榜、私有比赛文件和打印管理操作同样不会因全局管理权限而提前开放。该限制只影响当前请求，不修改账号角色；比赛结束后自动恢复 Hydro 原有权限。

- 比赛递交页支持即时搜索：输入题号（含 `AA`）、题目 ID 或标题片段，或输入用户名片段 / UID，均在本场比赛题目范围内搜索；题目候选列表只包含本场题目。状态、语言、分页与搜索组合使用，输入后自动更新，无需点击 Refresh；中文输入、快速连续输入和重置保持当前比赛及“我的递交”范围。
- “所有递交”和“我的递交”包含本场比赛记录及赛后补题。Hydro 原生补题提交不保存比赛 ID，因此赛后补题按“本场题目、比赛结束后的普通提交”纳入；不包含赛前普通提交、其他题目、其他比赛、预测试或其他域的记录。“我的递交”始终限定当前用户。实时推送使用相同筛选，评测状态变化后不符合筛选的行会自动移除；原有赛前/赛中权限和封榜规则继续生效。

## 安装

将本目录复制到 HydroOJ 的 `plugins` 或 addons 目录，并在 Hydro 配置中启用 `rating-system`。首次加载插件后可从管理脚本执行 `rating`，用于立即结算所有域中尚未计算 Rating 的比赛；传入 `domainId` 可只处理一个域。指定比赛重算和全部历史重算的用法见下文。

插件使用 Hydro 导出的 `ObjectId` 和 `Schema`，不需要在插件目录单独安装 `mongodb` 或 `schemastery`。如果日志出现这两个模块的 `Cannot find module`，说明服务器仍在运行旧版 `index.ts`；请完整覆盖插件目录后再重启 Hydro。

单机 MongoDB 结算兼容 `This MongoDB deployment does not support retryable writes` 报错：驱动可能将“不支持事务”的原始错误包装成这条提示，插件现在会检查原始错误并切换到可恢复提交。重启 Hydro 后，可重新执行 `rating` 或 `hydrooj script rating '{"domainId":"system"}'` 即可继续增量结算，无需使用 `full=true`，也无需为了这个事务兼容问题修改连接字符串。逐场输出的 `settled` 表示已完成计算，需以域级 `finished` 日志确认提交完成。全域脚本仍会继续处理其他域，但只要有域失败，最终就返回 `false`；每日任务也会报告失败。

插件会创建以下域用户字段：

- `internal_rating`：用于计算的内部实力分，可以为负数；
- `rating`：页面展示的当前 Rating，最低为 0；
- `rated_count`：有效 Rated 比赛场数；
- `max_rating`：历史最高展示 Rating。

对应的规则字段名为 `internal_rating`、`rated_count`、`max_rating`；camelCase 字段只用于兼容 Hydro 的现有模型和模板。

## 比赛配置

比赛开始前勾选 `Rated`，按需要填写 Rating 分段。最低值使用闭区间，最高值使用开区间；未填写时分别使用默认值 `0` 和 `10000`。**比赛一旦完成 Rating 结算，编辑页仍会完整显示全部比赛信息，但只允许修改比赛说明**；标题、赛制、开始/结束时间、题目列表、参赛语言、权限、文件、`Rated` 与 Rating 分段、比赛类型与排序规则、本场发布者和比赛管理员名单均为只读。服务端会忽略未变化的冻结字段并拒绝任何其他比赛配置变更，手工构造请求也不能绕过；Hydro 原生的赛后榜单解锁状态仍由其专用操作维护，不属于编辑页比赛信息。插件网页操作产生的校验和权限错误统一使用 Hydro 原生错误类型及 `error.html` 页面，不会进入系统故障页。未结算的比赛仍然可以修改全部原有字段。插件只对正式个人比赛生效，只有 XCPC、IO、IOI 三种类型可以结算；作业、虚拟/练习参赛、旁观参赛、系统 `unrank` 为真的参赛者和取消资格用户不会进入计分集合。比赛详情页直接显示 Hydro `unrank` 状态；字段未设置时显示为参与 Rating 排名。

## 流水与重算

不传重算参数时只计算未结算比赛，不重算已经结算的比赛，也不重复通知（命令行仍需提供空 JSON 参数）：

```sh
hydrooj script rating '{}'
```

指定本场比赛 ID 重算，域会从比赛记录中自动识别；`contestId` 取自比赛链接中 `/contest/` 后的 24 位 ID：

```sh
hydrooj script rating '{"contestId":"比赛的24位ID"}'
```

也可以明确指定域，`tid` 与 `contestId` 等价：

```sh
hydrooj script rating '{"domainId":"system","tid":"比赛的24位ID"}'
```

已结算比赛会从原始赛前 Rating 重算，并按原有结算顺序接续重算其后的已结算比赛，保持 Rating、计分场次和历史最高分连贯；之前的结算流水以及其他未结算比赛不变。尚未结算过的指定比赛则以当前 Rating 单独结算，不顺带计算其他未结算比赛。每次显式重算都会重新发送通知，即使结果数值没有变化。重复重算不会叠加同一场比赛的 Rating。比赛未结束、存在待评测记录、后续比赛无法完成重算或历史流水不完整时，不会保存部分重算结果。`contestId`/`tid` 不能与 `full=true` 同时使用。

完整重算全部历史仍使用：

```sh
hydrooj script rating '{"full":true}'
```

`rating.settlement` 保存比赛 ID、用户 ID、规则版本、赛前/赛后状态、实际名次、期望排名、目标排名、目标实力分、原始变化、两次统一修正、参考群体、展示补分、展示变化、结算批次以及通知发送状态等字段。日常计算只追加尚未计算 Rating 的比赛的流水，已结算比赛的流水保持原样，历史最高 Rating 因此始终是结算顺序上的累计结果。指定比赛重算只替换该场及其后续已结算比赛的流水，完整重算（`full=true`）才重建全部历史。

`rating.notification` 为普通结算和每次显式重算分别保存通知记录，与结算流水在同一提交中写入，字段包括比赛 ID、用户 ID、通知批次 `notificationRunId`、结算结果指纹、通知正文、状态（排队/发送中/已发送/失败）与存储批次。每次显式重算会重新通知，同一通知批次的重试不会重复发送。该集合默认无需清理，也可在确认历史通知不再需要重试后自行删除其中的 `sent` 记录。

参赛状态只使用 Hydro 原有的 `unrank` 字段，不创建插件专用的排名字段；没有有效提交的参赛状态不会生成用户 Rating 流水。


## 题目自动评级

题库每题的难度改为本站 **Problem Rating**，替换 Hydro 原来的手动 1–10 分与通过率估算法。题库列表、题目详情、侧栏、训练计划、题目编辑页使用同一份自动评级；题库增加评级筛选，也支持搜索 `difficulty:1600`，`difficulty:0` 表示待评级。题目编辑/创建页展示只读评级，服务端忽略对评级字段的手工写入。比赛中每题的满分仍使用比赛配置。

算法参考 [Codeforces 官方对题目难度的解释](https://codeforces.com/blog/entry/62865)：用选手实力和通过概率校准难度。这里实现的是本站估计器，并非 Codeforces 私有算法的逐字复现，也不会下载或套用 Codeforces 题目分数。

设本站用户历史内部实力分为 `R`，题目难度为 `D`，采用 `P(通过) = 1 / (1 + 10^((D - R) / 400))`。通过二分，使加权预计通过人数与实际通过人数吻合，再按 100 分取整，限制在 **800–3500**。实力分使用本站 Rating 计算中的 `internalRating`，避免新手展示补分与展示分截断干扰难度；选手相应时点的已计分场次决定权重 `max(0.25, min(1, ratedCount / 6))`。另外加入两份位于样本平均实力的中性先验，使全通过、全未通过和小样本不会产生无限评级。

每题至少需要 **5 位独立用户**才显示分值，少于 20 位时标注“暂定”。无数据、只有作者数据或有效样本不足时显示“待评级”，不回退到旧通过率算法，也不凭空给所有题填分数。

- 比赛样本来自已完成本站 Rating 结算、已经结束且已解封的比赛：使用冻结的赛前实力和当前最终评测结果；正式有效参赛者只要在本场有一次有效提交，就作为本场各题的观察样本，未通过题目按未通过处理。排除发布者、比赛管理员、打星、虚拟参赛、观察者和取消资格者。重测期间，保留已经发布且依赖该场比赛的上一次估计，待最终结果齐全后更新。赛后补题不会改变赛内通过结果。
- 题库普通练习以每位用户对每题的首次有效提交开始，观察固定 **24 小时**窗口；窗口内至少一次 AC 记为通过，否则记为未通过。成功与失败均等到窗口关闭后才进入样本，窗口后的 AC 和重复递交不会反复加权。实力取首次尝试之前的历史 Rating 流水，无历史时使用本站初始内部实力 1400。普通练习在任一比赛使用该题的比赛时间内产生的记录不进入练习样本。
- 同一用户、同一题在所有比赛和练习之间只保留最早一次独立观察；排除题目作者、维护者、系统账号、预测试、Hack、取消成绩、System Error、其他比赛和其他域的无关记录。公开文档只包含每题汇总样本量、通过数、估计版本和计算时间，不公开用户实力明细或来源比赛 ID；来源 ID 单独保存为不进入公开投影的 `problemRatingSources`，用于重测期间维持已有估计。

首次启用新版本会将旧难度备份到题目文档的 `legacyDifficulty`，将旧展示切换为待评级，并把各域题库放入持久更新队列。评测完成、题目新增/编辑、比赛信息更新后会标记相关题目；后台每分钟处理队列，每日补一次全量更新以覆盖练习窗口关闭。用户 Rating 正常结算、指定重算或完整重算完成后，也自动更新该域题目评级。题目更新与选手 Rating 结算共用域锁；未完成的选手提交会先恢复，更新失败、并发到来的评测事件均保留队列重试。

立即重新计算整个题库：

```sh
hydrooj script problem-rating '{}'
```

更新指定域，或请求更新单题（题号可用数字 ID 或 `P1000`）：

```sh
hydrooj script problem-rating '{"domainId":"system"}'
hydrooj script problem-rating '{"domainId":"system","pid":"P1000"}'
```

新难度写入原生 `difficulty` 数字字段，以兼容 Hydro 的查询和导出；`problemRating` 保存 `site_problem_rating_v1` 版本、评级、独立人数、通过人数、比赛/练习样本数、有效权重、暂定标志和计算时间。少样本时 `difficulty=0`、评级为 `null`。题目更新不会重新给用户发送比赛 Rating 通知。

## QQ 机器人只读 API

此接口供协会官网后台的 QQ 机器人服务调用，保留本插件原有 Rating、比赛权限、榜单、通知和题目评级功能。接口默认关闭，不需要提供 Hydro 登录 Cookie，也不会借用管理员的登录权限。

在 Hydro 的 `rating-system` 插件配置中设置：

```yaml
botApiEnabled: true
botApiSiteUrl: "https://oj.example.com" # 留空时使用 Hydro 的 server.url
botApiKey: "在此填写随机生成的密钥，并与协会官网后台填写的 Hydro API Key 保持一致"
```

密钥须为 32–256 个字符的随机字符串（允许 hex、base64 和 URL 安全字符），拒绝重复字符和明显的示例密钥。建议生成 32 个随机字节并转为 64 位 hex；例如在可信终端执行 `openssl rand -hex 32`。不要直接使用上述说明文字。请求必须通过 HTTPS，并只在请求头中携带 `X-API-Key: <密钥>`；URL 查询参数、Cookie、Bearer Token 和超级管理员身份都不能替代这个密钥。接口不会把密钥加入返回内容。

- `GET https://oj.example.com/rating-system/bot/contests`：返回 `{ "contests": [...] }`。每项包括 `id`、`title`、ISO 8601 UTC 时间 `beginAt` / `endAt` / `registrationStart` / `registrationEnd`、按 `botApiSiteUrl`（留空时使用 Hydro `server.url`）生成的 `url` 和布尔值 `rated`。仅查询 `system` 域中未来或进行中的公开比赛，排除作业、隐藏赛制、隐藏/私有比赛和按群组分配的比赛，按开赛时间升序最多返回 100 场。不接受任何查询参数。Hydro 原生没有报名开放时间，因而 `registrationStart` 默认为 `null`；原生规则允许未报名用户在赛完前报名，`registrationEnd` 默认为 `endAt`。若比赛文档有明确的 `registrationStart` / `registrationEnd` 或兼容字段，则返回这些时间；已经开赛的比赛不会因为报名结束而被移除。
- `GET https://oj.example.com/rating-system/bot/profile?email=<URL编码的邮箱>`：只接受一个最长 254 字符的有效邮箱字符串，返回 `rating`、`maxRating`、`ratedCount`、`level`、`color`、`solvedCount` 和 `difficulty: [{ label, count, percent }]`。邮箱遵循 Hydro 自身的账号匹配规则。返回值不包含邮箱、UID、角色、真实姓名、密码或提交代码。`level` / `color` 使用本插件现有段位规则。

账号匹配与 `paa-external-login` 保持一致：该插件把官网邮箱保存为 Hydro `user.mail`，并通过 `UserModel._handleMailLower` 生成 `user.mailLower`。本 API 同样调用 `UserModel.getByEmail('system', email)`；Hydro 会转小写、去除邮箱本地部分的点与 `+` 后缀，并兼容 `googlemail.com`。这里只查询已经存在的账号，不会调用外部登录、创建账号或写入域用户。官网用户尚未在 OJ 创建账号时返回通用 `404 { "error": "not_found" }`，机器人可提示先访问 `https://oj.example.com/login` 使用官网账号登录一次。

`ratedCount` 从 `system` 域**已经生效且有效的个人 Rating 结算记录**按比赛去重计算，并核验对应比赛已成功结算及个人计分次数递增。打星、无有效参赛资格、不计 Rating、未结算、人数不足、被取代和待提交的结算不会计入。优先用最后一次有效结算快照显示当前与最高 Rating，避免单机数据库恢复期间读到尚未生效的中间状态。

解题统计只使用 `system` 域中该用户当前仍为 AC 的记录，按本域现存题目去重；同一题重复 AC 只计一次，不混入其他域、其他用户、预测试、生成数据、Hack 或取消成绩记录。隐藏题仅计汇总数量，不返回题号或内容。难度使用本站自动 Problem Rating，分为 `800–1100`、`1200–1500`、`1600–1900`、`2000–2300`、`2400–3500` 和 `待评级`；旧难度或有效评级不足的题目归入待评级，各桶是互斥划分，`percent` 是该桶占本站总解题数的百分比（保留一位小数）。

两个接口只读，固定访问 `system` 域，拒绝重复/额外/对象形式参数，不把用户输入拼接为数据库操作或正则。数据库聚合设置 5 秒时限，接口使用数据库原子计数限流：每个 IP 每分钟 90 次（包含认证失败），同一密钥每分钟最多 60 次个人查询、180 次比赛查询。限流记录通过 TTL 自动清理，多进程共享限额。`rating_bot_solved` 索引用于加速用户 AC 统计。返回值设置 `Cache-Control: no-store`。

HTTP 状态：`200` 成功，`400` 参数错误，`401` 密钥错误，`404` 无匹配信息或当前请求域不支持，`429` 请求过多（`Retry-After: 60`），`503` 接口未启用、配置不可用或暂时无法查询。错误只返回通用 `error` 代码，不回显邮箱、私有用户资料、密钥或数据库错误。

## 开发验证

在已安装开发依赖及 `@hydrooj/ui-default` 的 Hydro 工作区根目录执行 `node -r @hydrooj/register --test plugins/rating-system/tests/*.spec.ts`。榜单与递交测试覆盖封榜数据、原生成绩、提交行兼容、未报名用户的赛后导航、题目与用户动态搜索、赛后补题范围、实时状态过滤、分页、重置及参赛身份组合筛选。题目评级测试覆盖实力校准、去重、时间窗口、重测、封榜隔离、历史快照、旧值迁移、队列恢复和筛选。数据库测试使用临时单机 MongoDB 和副本集验证增量结算、指定比赛与接续重算、通知批次、重复运行、失败恢复与错误报告，不访问 Hydro 配置的数据库，也不发送真实站内消息。首次运行可能下载测试用 MongoDB。

QQ API 测试使用临时 MongoDB，验证默认关闭、独立请求头认证、禁止查询参数密钥、管理员不能绕过、输入限长与注入拒绝、跨域/隐藏/作业隔离、AC 去重、Rated 流水去重与无效流水排除、私有字段投影、难度比例、并发限流和 TTL 索引，不连接正式 OJ 或发送 QQ 消息。

测试默认从已安装的 `@hydrooj/ui-default` 定位原生模板；使用不同 UI 包时，可通过 `HYDRO_TEMPLATE_DIR` 指定该包的 `templates` 目录。
